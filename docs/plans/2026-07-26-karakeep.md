deltas only. Delete this doc when it lands.

## Why there are three containers

The `karakeep` container does not fetch pages itself. Its crawler is Puppeteer driving a
remote browser over CDP (`BROWSER_WEB_URL`), and that browser is what produces the
rendered HTML for content extraction, the preview screenshot, and the optional archive.
Most bookmarked pages are client-rendered — a plain HTTP fetch returns an empty shell, so
title, content and AI tags would all come back blank. It is also the isolation boundary:
untrusted pages execute in their own container, not in the app process.

Meilisearch is full-text search. **No Postgres** — Karakeep is SQLite under `DATA_DIR`.

## 1. Ship dir — `going-merry/karakeep/`

Bind `100.64.0.1:3050` → container 3000. GM's taken ports: 3000 grafana, 3100 loki,
3200 dawarich, 6868 profilarr, 8095 your_spotify, 8428 victoriametrics, 9898 backrest,
11011 cleanuparr.

Meilisearch and chrome get **no published ports** — they're reached over the compose
network by service name. Only the web container is exposed.

`secrets.env` holds `NEXTAUTH_SECRET`, `MEILI_MASTER_KEY`, the Authelia client secret,
and the LiteLLM key. Generate the two random ones with `openssl rand -base64 36`, and
per the runbook do not pass them on a command line.

Env worth spelling out (names confirmed against the v0.32.0 docs):

| var | value |
|---|---|
| `DATA_DIR` | `/data` — the SQLite DB and the asset store |
| `MEILI_ADDR` | `http://meilisearch:7700` |
| `BROWSER_WEB_URL` | `http://chrome:9222` |
| `NEXTAUTH_URL` | `https://karakeep.siffreinsigy.me` — set it explicitly, same class of bug as Dawarich's derived redirect |
| `CRAWLER_FULL_PAGE_ARCHIVE` | `true` — off by default; this is the "the page 404'd and I still have it" feature, and the main reason this is on the disk-fast node |
| `CRAWLER_FULL_PAGE_SCREENSHOT` | leave default |
| `MEILI_NO_ANALYTICS` | `true` |

## 2. LiteLLM — the cross-node bit

Karakeep runs on GM, LiteLLM on TB. **This section is superseded by
[2026-07-27-cross-node-calls-use-the-public-edge](../ADR/2026-07-27-cross-node-calls-use-the-public-edge.md).**
It used to have LiteLLM bind `100.64.0.2:4000` and Karakeep dial it over the mesh. That is
exactly the bridged-container→tailnet call the mesh guard exists to forbid, and it would
have made the guard permanently un-installable on GM. LiteLLM now binds `127.0.0.1:4000`
only; `ai.siffreinsigy.me` already reverse-proxies its whole API, so the public edge is
not a wider surface than the mesh bind was.

Karakeep gets

```
OPENAI_BASE_URL=https://ai.siffreinsigy.me/v1
OPENAI_API_KEY=<its own LiteLLM virtual key, not the master key>
INFERENCE_TEXT_MODEL=<a model name defined in LiteLLM's config>
```

The model names must match LiteLLM's config list, not OpenAI's catalogue — Karakeep's
defaults (`gpt-4-mini`, `gpt-4o-mini`) will 404 against the gateway unless you happen to
have named them that.

**Do not route this over the mesh.** `the-sea-mesh-guard.service` now runs on both nodes
([why](../ADR/2026-07-25-mesh-guard-in-raw-prerouting.md)), so a GM bridged container
dialing `100.64.0.2` is dropped there too — and there's no GM→TB rule in the Headscale ACL
either. See the decision above.

## 3. Auth — OIDC, outcome (a)

Karakeep supports OIDC and Authelia ships an integration doc for it.

Redirect URI — **exact, no wildcard**:
```
https://karakeep.siffreinsigy.me/api/auth/callback/custom
```
`custom` is the NextAuth provider id and is not configurable. `require_pkce: false` and
`client_secret_basic`, per Authelia's own Karakeep client reference — the second client
after `profilarr` that can't do PKCE, and for the same reason it's acceptable: it's a
confidential client.

App side:

| var | value |
|---|---|
| `OAUTH_WELLKNOWN_URL` | `https://auth.siffreinsigy.me/.well-known/openid-configuration` |
| `OAUTH_CLIENT_ID` / `OAUTH_CLIENT_SECRET` | from `secrets.env` |
| `OAUTH_PROVIDER_NAME` | `Authelia` |
| `DISABLE_SIGNUPS` | `true` — **after the first login creates your account** |
| `DISABLE_PASSWORD_AUTH` | `true` |
| `OAUTH_ALLOW_DANGEROUS_EMAIL_ACCOUNT_LINKING` | leave unset. It is named that for a reason |

Caddy is a plain `reverse_proxy host.docker.internal:13050` — no `forward_auth`. Add a
`:13050 { reverse_proxy 100.64.0.1:3050 }` listener to `thriller-bark/gm-relay/Caddyfile`,
a row in REFERENCE's [GM relay table](../REFERENCE.md#gm-relay), and `tag:gm:3050` to
`thriller-bark/headscale/acl.hujson` — main Caddy is bridge-networked and can't dial the
mesh directly. Note the browser extension and mobile app authenticate with API keys
against `/api/*`; that path must not end up behind an edge gate later.

## Backups

- **DB + assets → GM bulk.** `backup.sh` in the service dir: `sqlite3 .backup` (or
  `VACUUM INTO`) inside the container onto `/var/backups/the-sea/dumps/` — **never `cp` a
  live SQLite file.** If the dump leaves the container via `docker cp`, `chmod 600` it
  yourself; the umask doesn't apply. The archived assets are the bulky half — mount the
  data volume `:ro` into GM's Backrest and add it to the bulk plan.
- **Meilisearch: skipped.** It's a derived index Karakeep rebuilds from the DB —
  the runbook's re-creatable-cache clause. Saying so here so nobody "fixes" the omission.
- Not critical-tier: bookmarks are re-crawlable, if tediously.

## Done when

Login goes through Authelia with password auth off, a bookmark crawls and comes back with
a title, screenshot and an AI-generated tag, search returns it, and a dump plus the asset
volume appear in a GM bulk snapshot.
