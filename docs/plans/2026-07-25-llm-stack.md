# Plan — LLM stack: LiteLLM + Open-WebUI (Thriller Bark)

One plan, two stacks — they're only useful together. Follows
`docs/runbooks/add-a-service.md`; deltas only. Delete this doc when both land.

**Shape:** LiteLLM is the single gateway; **Open-WebUI and n8n both point at it** so
keys and cost tracking stay in one place. **Hosted APIs only, no Ollama** — TB is ARM
and CPU-only. Call logging and cost go to the existing Grafana/Loki; **LangFuse is
dropped** (Clickhouse + MinIO + Redis + Postgres is not worth it when the
observability stack already exists).

**Pins, resolved 2026-07-25** — re-check on deploy day, both projects ship weekly:

| | image | source |
|---|---|---|
| LiteLLM | `ghcr.io/berriai/litellm:v1.93.0` | release `v1.93.0`, 2026-07-19; manifest HEAD → 200 |
| Open-WebUI | `ghcr.io/open-webui/open-webui:v0.10.2` | release `v0.10.2`, 2026-07-01 |

**TB is ARM — both manifests carry `linux/arm64`** (index inspected 2026-07-25, not
just a 200 on the tag). No node-placement problem. Same check passed for
`gethomepage/homepage:v1.13.2` and `wizarrrr/wizarr:v2026.7.1`.

Two traps found while resolving these, worth keeping:

- **The GHCR tags list caps at 1000 and is not in date order** — the `jq '.tags[]'`
  one-liner this plan used to carry gives a misleading answer for busy repos (LiteLLM's
  list ends at v1.66). Get the version from
  `GET https://api.github.com/repos/<owner>/<repo>/releases/latest`, then *confirm the
  image tag exists* with a manifest HEAD:
  ```bash
  r=berriai/litellm; tag=v1.93.0
  t=$(curl -s "https://ghcr.io/token?scope=repository:$r:pull" | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')
  curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $t" \
    -H 'Accept: application/vnd.oci.image.index.v1+json' \
    "https://ghcr.io/v2/$r/manifests/$tag"
  ```
  (`jq` is not installed here; `python3` is.)
- **LiteLLM's tag naming.** `main-v1.93.0-stable` — the shape their docs historically
  used — is a **404**. `v1.93.0` and `main-stable` are the tags that exist. Upstream's
  own `docker-compose.yml` now also points at `docker.litellm.ai/berriai/litellm`
  rather than GHCR; GHCR still serves it, so stay on GHCR like everything else here.

## 1. LiteLLM — deploy first

**Node TB.** Bind **both** `127.0.0.1:4000` and `100.64.0.2:4000` (TB's mesh IP).
**No Caddy route, no Authelia** — it's internal, authenticated by its own API keys. This
is the one app in the fleet that stays off the edge entirely; don't "helpfully" add a
route.

The mesh bind is not a softening of that: the mesh is not the edge, and it is the same
reasoning by which every GM service binds `100.64.0.1`. It exists because **Karakeep runs
on GM and uses this gateway** (`docs/plans/2026-07-26-karakeep.md`) — without it, Karakeep
would have to hold provider keys directly, which is the thing this stack exists to
prevent. Each consumer gets its own virtual key, never the master key.

- Config is a YAML model list (provider, model name, `api_key` as an env reference) —
  plain committed file, bind-mounted, so the stack needs
  `extra_args = ["--force-recreate"]`.
- Provider API keys and the LiteLLM master key into `secrets.env`. Never in the YAML.
- **Reversed 2026-07-27: Postgres is in, now.** This section used to say skip the DB
  unless per-key budgets become a real need. The admin UI *is* the key and spend store,
  so wanting the UI is wanting the database — the deferral ended on day one instead of at
  Phase 4. It's a `pgvector/pgvector:0.8.5-pg17` in the same stack, on TB, with no host
  port; see [the decision](../decisions/2026-07-27-postgres-on-thriller-bark.md) for why
  it isn't on GM. `STORE_MODEL_IN_DB` stays off so the model list is still committed YAML.
  Health endpoint for the compose healthcheck: `GET /health/liveliness`.

  **Caddy route, also new:** `ai.siffreinsigy.me` behind `forward_auth`, **admin UI only**.
  The whole host is gated, not `path /ui*` — the UI XHRs to root-level endpoints
  (`/model/info`, `/key/list`, `/spend/logs`), so a path split serves a page that loads
  and shows nothing. `/v1/*` stays unrouted; every consumer reaches the gateway privately.
  Exposing the API publicly is a separate decision when it's actually wanted.

## 2. Open-WebUI — after LiteLLM answers

**Node TB.** Bind `127.0.0.1:3020` — **not** 8080, that's headscale. TB's taken ports:
8080 headscale, 9091 authelia, 9120 komodo, 9898 backrest, 5006 actual, 5678 n8n,
12345 alloy. Host `chat.siffreinsigy.me`. Fresh build: the legacy
`docker-mei/open-webui/webui` dir was **deleted intentionally** and is not in the
archive, so there is nothing to restore.

- Points at LiteLLM as an OpenAI-compatible backend. **Var names confirmed** in
  `backend/open_webui/config.py` at v0.10.2: `OPENAI_API_BASE_URL` and `OPENAI_API_KEY`
  = a LiteLLM virtual key.

  **`http://127.0.0.1:4000/v1` will not work** — corrected 2026-07-26. Inside a bridged
  container `127.0.0.1` is that container's own loopback, and TB's host gateway is closed
  by the `INPUT` default REJECT recorded in `domains/networking.md`. Both containers must
  join the shared `the-sea-internal` network and dial `http://litellm:4000/v1` by
  container name. Create it once on TB with `docker network create the-sea-internal` and
  declare it `external: true` in both composes. Full reasoning, and the other consumer of
  that network, in `docs/plans/2026-07-26-paperless-ngx.md` §0.
  (Plural `OPENAI_API_BASE_URLS` / `OPENAI_API_KEYS`, `;`-separated, also exist — not
  needed for one backend.)
- Set `WEBUI_URL=https://chat.siffreinsigy.me`. The OAuth redirect URI is built from
  `request.url_for(...)`, so behind Caddy it will otherwise derive `http://` — this is
  literally the Dawarich failure again.
- Default Postgres/SQLite: **SQLite is fine** for a single user — one less container,
  one less dump.

### Auth — OIDC

Open-WebUI supports OIDC, so per §3b(a) it gets a real Authelia client, not
forward-auth. New client in `thriller-bark/authelia/secrets.oidc.yml`
(`client_id: open-webui`, hashed secret, explicit `redirect_uris`).

**Callback paths, read off `main.py` at v0.10.2** — two routes are registered for the
same handler, and `url_for('oauth_login_callback')` resolves to the **first**:

```
https://chat.siffreinsigy.me/oauth/oidc/login/callback
https://chat.siffreinsigy.me/oauth/oidc/callback         # marked "Legacy endpoint" in main.py
```

Put **both** in Authelia's `redirect_uris` — which one `url_for` actually picks depends
on decorator registration order, so don't try to predict it. Listing both costs nothing
and survives them reordering. (`oidc` is the provider slug for a generic OIDC provider.)

**PKCE: turn it on.** `OAUTH_CODE_CHALLENGE_METHOD=S256` is supported (config.py
v0.10.2 rejects any value but `S256`), so this client gets `require_pkce: true` in
Authelia — unlike the `profilarr` client, which can't. Note the code treats
`OAUTH_CLIENT_SECRET` *or* a challenge method as sufficient; keep the secret too.

Env vars for the "single user by config, not by hope" part, all confirmed at v0.10.2:

| var | value | why |
|---|---|---|
| `OAUTH_CLIENT_ID` / `OAUTH_CLIENT_SECRET` | from `secrets.env` | |
| `OPENID_PROVIDER_URL` | Authelia's `.well-known` issuer | required, or OAuth stays off |
| `OAUTH_PROVIDER_NAME` | `Authelia` | button label, default is `SSO` |
| `OAUTH_SCOPES` | default `openid email profile` | leave it |
| `ENABLE_SIGNUP` | `False` | kills local account creation |
| `ENABLE_PASSWORD_AUTH` | `False` | **the actual backend gate** — corrected 2026-07-26 |
| `ENABLE_LOGIN_FORM` | `False` | cosmetic only: hides the form, but `/signin` still accepts a POSTed password |
| `ENABLE_PASSWORD_CHANGE_FORM` | `False` | |
| `ENABLE_OAUTH_SIGNUP` | `True` **for the first login only**, then `False` | default is already `False`; you need one pass to create your account |
| `OAUTH_MERGE_ACCOUNTS_BY_EMAIL` | leave `False` | default; flipping it is an account-takeover footgun |
| `OAUTH_ALLOWED_DOMAINS` | your email domain | defaults to `*` |

`ENABLE_OAUTH_ROLE_MANAGEMENT` stays `False` — no group plumbing for one user.

### The trap: half those vars are only a first-boot seed

v0.10.2 keeps a `DEFAULT_CONFIG` dict and persists it into the database, and the
split is **not** intuitive (`config.py`, ~L2750–3135):

- `ENABLE_PERSISTENT_CONFIG` defaults **`True`** → `ui.enable_signup`,
  `ui.enable_login_form`, `openai.api_base_urls`, `openai.api_keys` are read from the
  env **once**, then the DB copy wins forever. Editing `secrets.env` later does
  nothing, which is exactly the kind of silent no-op that leaves signup open.
- `ENABLE_OAUTH_PERSISTENT_CONFIG` defaults **`False`** → every `oauth.*` key
  (client id/secret, provider URL, `oauth.enable_signup`, `code_challenge_method`,
  `allowed_domains`, `merge_accounts_by_email`) is re-read from the env on every boot.

So **set `ENABLE_PERSISTENT_CONFIG=False`** and leave `ENABLE_OAUTH_PERSISTENT_CONFIG`
at its default. Then the env file is the single source of truth for the whole app,
config-as-code like everything else here, and the `ENABLE_OAUTH_SIGNUP` true-then-false
step above actually takes effect on restart instead of being decorative.

### n8n wiring

Once LiteLLM is up, point n8n's LLM nodes at LiteLLM with their own virtual key. This is
the reason LiteLLM exists; don't skip it and let n8n hold provider keys directly.

**Corrected 2026-07-27: not `http://127.0.0.1:4000/v1`.** n8n is a bridged container too,
so its `127.0.0.1` is its own loopback — the exact bug already fixed for Open-WebUI above.
n8n joins `the-sea-internal` as well and dials `http://litellm:4000/v1`. Same host, still
no mesh hop.

## Backups

- **LiteLLM:** the Postgres landed, so this is the critical path, not the "later" one.
  `thriller-bark/litellm/backup.sh` (`pg_dumpall` piped to stdout, `umask 077`, atomic
  `.part` + `mv`) → **critical** plan: virtual keys and spend logs are secrets material.
- **Open-WebUI:** its data volume holds chat history and settings → `backup.sh` if it
  ends on Postgres, otherwise mount the volume `:ro` into TB's Backrest and add it to
  the **bulk** plan. Chats are not critical data.
